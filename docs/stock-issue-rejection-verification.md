# Retained rejection of pending stock issues

October 28, 2026. This release adds a missing owner decision for a mistaken, still-pending request. It does not establish the cause or value of the historic reported shortage, certify physical inventory or certify prolonged use on an actual cashier PC.

## Problem and behavior

Previously the pending damage/spillage/other-issue worklist offered approval only. A mistaken request could remain awaiting approval indefinitely. Online owners can now reject it with a reason. The original request remains intact, becomes terminal and appears in a paginated rejected-history list with its exact measurement, original evidence, decision ID, owner name, reason and Manila date. Stock, held goods, cash, purchase-cost losses and investigation state remain unchanged.

Approved issues cannot be rejected. Rejected issues cannot later be approved, edited, deleted or reopened. A corrected request requires a new identity after evidence review. Dependent receiving/refund corrections still need their existing reconciliation procedure; this is not a force-undo control.

## Server, recovery and permissions

The new decision uses the existing current-session, active membership, organization/branch and stock-role checks, then requires the owner role. Both approval and rejection acquire the same authorized branch transaction lock before checking terminal state. Exactly one competing decision can succeed. Rejection changes the request state and appends its decision/audit evidence atomically, with a unique per-request rejection index. Owner names are frozen in decision audit evidence. A trigger protects rejected originals even from ordinary maintenance updates/deletes. No table grant, browser privileged key, dependency or local schema version was added.

The command persists one `decisionId` through the existing IndexedDB pending-operation mechanism before uploading. Identical retries return the first acknowledgment; changed contents or actors under that ID conflict. A new decision ID cannot reject an already rejected request. Recovery files recognize the new command and preserve its original ID, actor and fingerprint. Uncertain requests stay recoverable. Server-confirmed rollback follows the established queue rules. The read response adds fifty rejected rows and timestamp/UUID continuation while preserving all existing held/pending counts and cursors.
