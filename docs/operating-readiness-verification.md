# Operating checks, store guide and interrupted access

October 28, 2026. The [store-use and readiness plan](store-readiness-plan.md) maps routine work and incidents to the delivered controls, evidence and remaining gaps. It does not certify unchosen hardware, physical opening inventory, real staff rehearsal, actual production-backup restoration or a one-branch pilot.

## Implemented

Settings now includes **PC checks & store guide**, after the existing shift/recovery controls. It reads all unresolved local sales through their status index, independently of the fifty-recent-receipt display. It aggregates permitted branch/employee counts, authentication/review states and uncertain owner/stock requests. Other-account records produce a count-only preservation warning, never their request contents. Counts are read in one IndexedDB transaction and do not change records or upload anything. Read failure removes the old checks and asks staff to stop affected checkout and preserve evidence rather than showing a false clear queue.

The same section shows the saved catalog timestamp, missing/stale/future snapshot guidance, cashier authorization with a running countdown, unavailable/unprotected/low browser storage, and active application-cache observation. Storage quota and browser-reported online state are explicitly limited observations. Neither an active worker, persistence, a recent snapshot nor an empty queue becomes a launch-ready badge. Closed shifts and stock-staff work remain distinct from authorization to sell. The refresh control reads locally; a separate online-only stock/catalog control uses the existing fenced snapshot workflow. Check data refreshes on focus or explicit request; current authorization time continues updating. Late/unmounted check responses cannot replace another account's result.

Sixteen native expandable procedures cover opening, measured/peso/piece selling, unclear save, outages/restart, expired/revoked access, inspected receiving, receiving corrections, partial transfers, held/expired/damaged goods, independent counts, loss costing, partial refunds/corrections, printing, closing, recovery and maintenance. They ship in the application bundle and are available with the cached application. They create no stock/cash effect and do not enable offline-only privileges or replace the real operating gates. There are no self-certified readiness checkboxes.

## Reproduced synchronization gap and fix

`syncOnce` verified access before each batch, but an authentication/authorization failure during a later upload fell through the network-backoff path. Repeated failures could spend the network retry allowance and become owner-review records for a sign-in problem. The upload catch now recognizes explicit authentication signals, JWT failures, 401/403 responses and permission revocation, pauses the batch as authentication-required and retains attempts, delay, payload, fingerprint and original transaction IDs. It skips the unauthorized snapshot. Renewed verified access follows the existing authorize path before any retry.

The pause runs in a local transaction with the existing settings/runner-lock fence. It preserves any record already confirmed by a concurrent authoritative snapshot and any genuine owner-review result returned earlier in that batch. A committed-but-unconfirmed upload remains recoverable; its retry reuses its ID and the server returns its original acknowledgment. Ordinary network failures retain their existing backoff. Completed history is neither deleted nor rewritten. The schema, sale contracts, recovery archive version, dependencies and server permissions are unchanged.

Online command errors now explain expired sign-in separately from refused permissions while retaining the original error code and status. The message warns that sign-out clears an unfinished basket, asks for the original employee and original-request retry, and preserves saved sales. No automatic sign-out, password change or privilege widening was added.

## Native-timeout classification gap

Review also found that the browser-side upload and pending-operation handlers tested error codes using a prefix regular expression without checking their type or full SQLSTATE length. A native `DOMException` named `TimeoutError` carries numeric code **23**. If that native exception reaches either handler, JavaScript's string coercion could classify it as SQLSTATE integrity class 23: uploads could become permanent review acknowledgments and an uncertain stock request could be removed from the pending queue. This is a classification defect; no hosted instance of data loss is claimed.

Both handlers now share a predicate that accepts only complete five-character database SQLSTATE strings in the existing rollback classes. Numeric native codes and incomplete strings remain ambiguous. Timeouts therefore preserve the original pending request, generated ID, fingerprint and recovery export; uploads keep the ordinary network failure path. Thirteen added regression cases exercise actual native timeout/abort exceptions, numeric and incomplete codes, confirmed SQLSTATEs, sale-upload rethrow, repeated receiving timeout, recovery export and duplicate acknowledgment of the original receiving ID. They do not replace a real cashier-PC network or storage failure test.
